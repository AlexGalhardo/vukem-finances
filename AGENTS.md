# AGENTS.md

Guide for every agent that works in this repository. `CLAUDE.md` points here.

## What the project is

vukem-finances is a personal finance application built with [Vukem](https://vukem.dev): Go on the server, React with Inertia and Tailwind in the browser, SQLite by default. It has accounts, categories, transactions, monthly budgets, a dashboard and CSV import, on top of sign-up, workspaces with roles, and Stripe billing.

The app ships in two editions of one binary (decision D-003), chosen by `APP_EDITION` (`config.LoadEdition`; unset means `personal`, any other value besides `personal` and `saas` stops the boot):

| | `personal` | `saas` |
| --- | --- | --- |
| Workspaces | one implicit workspace, made by `/setup` | one per user plus created ones |
| Sign-up | closed: `/register` is 404; the first owner uses `/setup` with `SETUP_TOKEN` or the code in the boot log, the others use `/invites/{token}/register` | public `/register`, email verification always on |
| Billing, `/stripe/webhook`, `/abacatepay/webhook`, `/admin/revenue` | not registered (404), no Stripe or AbacatePay settings read | registered |
| Plan limits | none (`workspaces.Personal`) | Free and Pro |
| `GET /` | redirects to `/dashboard`, `/login` or `/setup` (never to another site: it works offline) | redirects to `/dashboard` or `/login`; the app has no landing page, `site/` is the landing |
| Social login | find-only, never creates a user | creates users |

Ask the edition in one place: `workspaces.Service.Edition`, or `config.LoadEdition(app.Source)` where there is no service. Never read `APP_EDITION` in a handler. The finance test suite builds the app as `saas` (`newSaaSApp`); use `newPersonalApp` for the other edition. A sign-up address is never marked verified in `saas` (`AUTH_REQUIRE_EMAIL_VERIFICATION` is forced on, and a production boot refuses `false`).

## The static site

Read `docs/site.md` and `docs/landing-brief.md`. `site/` is 100% static (D-019, D-020): no backend, form, sign-up, login, checkout, cookie or third-party resource, and the page never says a hosted service exists.

- Every factual sentence of the landing page is a row of the claims register in `docs/landing-brief.md` with evidence in this repository; `cd site && bun run check:claims` checks it. Do not claim what has no evidence (the mobile app, MCP and store availability are not claimed until they ship).
- Copy lives in `site/src/landing/copy/<locale>.json` (identical keys in `en`, `pt-br`, `es`). The plan limits come from `site/generated/plans.json`, which mirrors `app/workspaces/limits.go`: change the limits, then run `go run ./cmd/app plans:export`.
- Run `bun install --frozen-lockfile`, `bun run typecheck`, `bun run check:claims`, `bun run test:site`, `bun run build` and `bun run check:built` in `site/` before a hand-off. Dependencies are pinned exactly; no animation or 3D library, no web font from a CDN.
- The documentation (epic 23, `site/content/docs/` written by hand, `site/content/generated/` generated) is plain Markdown listed in `site/content/navigation.ts`. Never edit a generated page: change its source (`docs/openapi.json`, `resources/operations.json`, `docs/reference/cli.md`, `docs/reference/mcp.md`, `.env.example`, `docs/shortcuts.md`, `CHANGELOG.md`) and run `bun run reference`. A page may only name a CLI command, setting, repository path, REST route, MCP tool, link and anchor that exist (`bun run check:claims` names the page and line). It says the personal edition is 100% offline (D-027) and that the SaaS edition is self-hosted with no hosted service offered.
- Before a hand-off also run `bun run check:mdx`, `bun run reference:check`, `bun run last-updated` and `bun run check:last-updated` in `site/` (`last-updated` rewrites `content/last-updated.json` from git: commit it with the page change).
- DNS, the Pages custom domain and `LANDING_TERMS_APPROVED` are manual steps of the author, never a task.

## The desktop app

Read `docs/desktop.md`. `desktop/` is a separate Go module (the root `go build ./...`, `go test ./...` and the Docker image do not see it); run `cd desktop && go vet ./... && go test ./...` for it, and `bash desktop/scripts/smoke.sh` for the headless smoke test.

- The desktop runs the personal edition on `127.0.0.1` behind `app/desktopgate`, which wraps the whole handler: loopback peer and Host, no proxy headers, same-origin fetches, and the `vf_desktop` cookie from the one-time launch token. Never mount a route or a static file outside the gate, and never serve the app on another address.
- `desktopgate.Verified(ctx)` is the only way a request skips the setup code; it is false when no gate wraps the handler. Do not read the cookie anywhere else.
- The desktop reads no `.env` and no process variable (`desktop/server.go` `desktopEnv`); add a setting there, not in the user's shell.
- The Wails runtime ignores a page it does not serve, so native actions go through `/desktop/*` routes of `desktop/gate.go` (save, open-external) and `desktop/shell.js`, not Wails bindings.
- Wails is pinned to an exact stable version in `desktop/go.mod` (no nightly, beta or alpha); the `wails3` tool is installed at the same version. Builds are unsigned.

## The application shell

Read `docs/design.md`, `docs/design-system.md` (the full specification and the migration plan) and `docs/shortcuts.md` before touching the UI. The design is original (D-011, D-012): another product may inspire a quality, never code, assets, copy or identity. The palette is white, black and the brand green `rgb(0, 158, 0)`; use `--vf-brand-text` for green text, never white or small text on the green fill. UI uses shadcn/ui (pinned `bunx shadcn@4.23.0`), Geist fonts and `lucide-react` only.

- **Add a sidebar item.** Append an entry to `resources/js/nav.ts` (`id`, `labelKey`, `href`, `icon`, optional `keys`, optional `edition: "saas" | "personal"`). The sidebar, the palette and a `go-<id>` action come from it. Billing is `edition: "saas"`: the personal edition must never show billing, workspace creation or workspace switching.
- **Sidebar groups, hints, help, tutorial.** A nav item sets `group` (money, planning, insights, data, settings) and, when its shortcut belongs to another action, `actionId`. A button shows its shortcut with `shortcutAction="<action id>"` (never a hand-written key). `HelpHint` and `TermHint` (`resources/js/help/`) read the `help` i18n domain. The tutorial (`resources/js/tutorial/`) highlights `data-tour="<target>"` attributes: a screen task adds the attributes its steps name, and a missing target falls back to a centered card. The tutorial never writes, keeps progress in `localStorage` (`vf.tutorial.v1.<userId>`) and is mounted by `layouts/Shell.tsx`. The theme buttons stay the last controls of the top bar and the sidebar footer holds only Account and Documentation (`e2e/shell-chrome.spec.ts`).
- **Register an action.** Call `useAction({ id, labelKey, group, keys, run, enabled })` from `resources/js/shortcuts/useAction.ts` in the component that owns the behavior. Never add a `keydown` listener. The action appears in the command palette and in the shortcut help by itself. Pick `keys` from the free ones in `docs/shortcuts.md` and add the row there; `registerAction` throws on a duplicate id or key, on a key a longer sequence starts with, and on a browser-reserved combination (`shortcuts/reserved.ts`).
- **Shortcuts never fire while the person types** (`shortcuts/guard.ts`). Mark a custom widget that takes text with `role="textbox"`, `combobox` or `searchbox`, or `data-shortcuts="off"`.
- **Add translations.** Add `resources/js/i18n/en/<domain>.ts`, `pt-BR/<domain>.ts` and `es/<domain>.ts` (the last two use `satisfies Record<keyof typeof en, string>`), then add one `typeof` line for the new domain to `resources/js/i18n/keys.ts`. `bun test resources/js/i18n` fails when a locale misses a key.
- **Page structure.** A signed-in page renders `PageHeader` for its one `h1`; the shell moves focus there after a navigation. Show money with `MoneyText` (sign or label, never color alone) and lists with `DataTable`. A settings page (Workspace, AI, Billing, Telegram, Tokens, Devices, TwoFactor) is a stack of `components/settings/SettingsSection` rows. A signed-out page renders inside `AuthLayout` with `components/auth/AuthParts` and `hooks/useFocusFirstError`, and the panel screens (`pages/Admin/*`, Revenue included) render inside `layouts/AdminLayout`, which mounts its own tutorial.
- **Tests.** `bunx playwright test` runs the browser specs in `e2e/` against the real server (`e2e/prepare.mjs` builds the app and seeds a throwaway database; set `E2E_CHANNEL=chrome` to use the installed Chrome, otherwise run `bunx playwright install chromium` once). `bun run test:js` runs the unit tests (`bun test resources/js`; the path is required). `@types/bun` is not installed: `resources/js/bun-test.d.ts` holds the few ambient types the tests use; extend it when a test needs another matcher.

## The public API

Read `docs/api.md` first. The API is `/api/v1`, bearer tokens only (the session and CSRF middleware skip the prefix, so a cookie is ignored); it exists in both editions.

- A token (`vf_<id>.<secret>`, only a SHA-256 of the secret is stored, shown once on the Tokens page) is bound to one workspace through `access_tokens.resource` and to the person who made it. Scopes are a ceiling: every request intersects the scope with the person's role now (`workspaces.RoleCan`). No `*` scope exists, and a token with one is refused. Removing a member revokes their tokens of the workspace.
- Every operation is declared once in `app/operations/` (see "The operation registry"); the REST row in `app/api/operations.go` only says where it is served (name, method, path, tag, status): the scope and the summary come from the registry, and the routes, the OpenAPI document (`x-required-scope`, D-017) and the scope matrix read them. `me.show` and the `sync.*` operations are REST only and keep their own row. To add an endpoint: declare the operation (and the scope in `app/operations/scopes.go` if new), add its row and its `route(...)` line in `API.Routes`, regenerate `docs/openapi.json` and `clients/typescript/api.ts` with `UPDATE_OPENAPI=1 go test ./tests/... -run 'TestOpenAPISnapshot|TestTypeScriptClientIsFresh'` and `resources/operations.json` with `go run ./cmd/app operations:inventory`, and add the case to `matrixCalls` (`tests/api_scope_matrix_test.go`), to `isolationCases` (`tests/operation_isolation_test.go`) and, for a `{uid}` path, to `apiCrossTenantCases` in the cross-tenant matrix.
- Nothing in `app/api/` calls a finance service (`TestAPIHandlersGoThroughInvoke`): a handler binds the input and calls `operations.Invoke`, and an operation holds no rule either. Amounts become text for `finance.ParseAmount` through `centsText`; the uid of a row is turned into its id with `c.accountByUID` and the like in `app/operations` (workspace scoped, a foreign uid is a 404); lists reuse `TransactionPage`. Money on the wire is an integer `*_cents`; ids on the wire are uids.
- Errors are problem+json with a stable `code` (`api.CodeOf`, set by the `ProblemDecorator` in `routes/api.go`). The failure order is 401, 404 (not a member), 429, 403, then 404 for a row of another workspace.
- The app serves only `/api/v1/openapi.json`; the reference is rendered by the static docs site (D-021). Never import the framework's `apidocs` package (`TestNoAPIDocsPage`).
- Rate limits are per token (120 reads and 60 writes a minute, `config/api.go`) and per address for failed lookups (60 a minute, refused before any lookup).

## The operation registry

Read `docs/api.md` ("Adding an operation") first. `app/operations/` is where every action a person or an agent can take is defined, so the REST API, and later the CLI and MCP (epics 31 and 32), offer the same operations with the same validation, permissions and results (epic 30).

- An operation is `operations.Define` of an `Operation[In, Out]`: `Name` (`resource.verb`), `Summary`, `Scope`, `Kind` (`read`, `write`, `destructive`), `Idempotent`, `Editions`, `OptOut` (a surface it is not offered on, with the written reason) and `Run(ctx, actor, in)`. `Ability` is set only for an operation that asks more or less of the role than its scope implies (`export.workspace` keeps the owner and admin rule; a goal contribution asks the recording ability).
- `Run` never receives a workspace id from its input: the `Actor` (user, workspace, role, scopes, surface) is built only by an authenticated adapter (`NewActor`, after the token and the membership were checked) or, in the personal edition, by `LocalOwner`. `Invoke` puts the tenant and the role of the actor in the context.
- `Invoke` is the only way to run an operation and adapters cannot skip a step: edition, scope, role, input validation (the `validate` tags), the idempotency key of a write (24 hours, per caller, a failed call frees its key), the call, and the audit entry of a write or destructive call (a structured log line `operation` with the name, kind, surface, workspace, user and outcome; never an amount, a description, a name or a uid). The REST adapter (`app/api/adapter.go`) also runs the gate early, as the `Require` middleware, so a refused call is refused before its body is read.
- Errors carry a stable code (`not_found`, `forbidden`, `validation_failed`, `conflict`, `rate_limited`, `plan_limit`, `internal`, plus `missing_scope` and `version_conflict`). `Error.Err` is the cause, which a REST client has always received as the problem+json; an internal error has a generic message and its detail stays on the server.
- A list that pages uses the opaque `operations.Cursor`. The lists of epic 14 keep their public contract (`?page=N`); the page links are built by the REST adapter, because a URL belongs to the surface.
- `resources/operations.json` is the inventory, written by `go run ./cmd/app operations:inventory` (no APP_KEY, no database) and checked by `TestOperationInventoryIsFresh`. `TestSurfaceParity` iterates the registry and fails when an operation has no route on a surface it is offered on (epics 31 and 32 add their surfaces to it); `TestOperationIsolation` runs every entry of the inventory in another workspace with the first one's ids; `TestOpenAPIOperationsOfEpic14DidNotChange` holds the published operations to `testdata/openapi/epic14.json`.
- The CLI (`app/cli/`, epic 31) builds a command from every operation offered on the CLI surface; flags come from the input type. Local mode runs through `Invoke` as the personal owner; remote mode calls REST with a token (`FINANCES_TOKEN`, `auth login`, never a flag). Table and CSV text passes through `cleanText` and the formula guard (`csvSafe`); a destructive command needs `--yes` without a terminal. `docs/reference/cli.md` is generated: `go run ./cmd/app cli:reference` (checked by `TestCLIReferenceIsFresh`); `TestSurfaceParity` fails when an operation loses its command.

## The MCP server

Read `docs/mcp.md` first. `app/mcp/` maps the registry to the Vukem `mcp` package (revision `2026-07-28`); it holds no protocol and no rule. `mcp:serve --stdio` is the personal edition only (it acts as `operations.LocalOwner`); any other edition exits before it serves.

- A tool is an operation: `Op.AddTool` (`app/operations/mcp.go`) registers it and calls `Invoke`, so scope, role, validation and audit are the registry's. The tool name is the operation name with `_` for `.` (`transactions_create`). A new operation gets a tool by itself (`TestSurfaceParity`); one that has none says why in `OptOut[SurfaceMCP]` and `docs/reference/mcp.md` lists it.
- Read only by default: `MCP_TOOLSETS` (`read`, `transactions`, `planning`, `all`) and `MCP_ALLOW_DESTRUCTIVE` (`config/mcp.go`). A tool outside the toolset is not registered and the actor holds no scope for it. A destructive tool also asks the person through `mcp.Confirm` and is refused when the client cannot ask; annotations are hints, never the enforcement.
- Put a new operation in a toolset in `InToolset` (`app/mcp/server.go`) and keep `TestToolsets` inside its size budget, or raise the budget on purpose.
- A result is the user's data: never add text from a result to an instruction, a prompt or a log. A prompt argument goes through `quoted`. A result never carries a secret (`TestSecurity_NoSecretLeaves`).
- Stdout is for protocol messages only: log to stderr, never print in `app/mcp` or in `mcp:serve`.
- Remote MCP (epic 33, saas only, `routes/mcp.go`, `app/oauth/`): `/mcp`, the metadata, `/authorize`, `/token` and `/revoke` are registered only when the edition is saas and `APP_URL` is https. The protocol is the framework's (`oauth`, `mcp`); `app/oauth` holds the store (a grant's `sub` is `<user>:<workspace>`, bound in `mcp_grants`, with the scopes approved at consent), the consent decision and the connected-apps list. Never widen what a grant holds: the verifier and `remote.actor` read the live membership, the scopes are cut to the role at consent and at every call, and every way that ends a person's access (`revokeAccess`, `RevokeOtherSessions`, `revokeTokens`) must also end their grants. A resource read, a completion and a tool call all pass the `Before` and `Done` hooks (`readOp`, `gate`). A client named by a metadata document is shown by its verified host, never by the name it claims. Tests use `app/oauth/oauthtest`; build token-shaped values at run time.
- `docs/reference/mcp.md` is generated: `go run ./cmd/app mcp:reference` (checked by `TestMCPReferenceIsFresh`).

## The AI layer

Read `docs/ai.md` first. AI is bring your own key (D-007): off by default, enabled by the workspace owner (`ai.manage`, owner only), never paid by the service.

- Every feature calls `ai.Client.Call(ctx, workspaceID, ai.Request{Feature: ...})`: it checks enabled, feature, key, 20 calls per minute and the monthly limit, then records `ai_usage`. Never call a provider directly and never build an `http.Client` for one (`ai.NewHTTP`: safe client, 30 s, 1 MiB, no redirects, one retry).
- The key is an `ai.Key` (prints `[redacted]`), stored sealed with `ai-key:<workspace>:<credential>` as additional data. It must not appear in a response, page prop, flash, log, audit event or export. The form field is `apiSecret` so the framework never flashes it back. Provider error text is never passed on or logged: `ai.ProviderError` keeps only the status and a plain error type.
- Pass every free-text field through `ai.Redact` before it goes into a request, and send only what the owner agreed to (description, amount, date, category names).
- A custom base URL (`openai_compatible`) goes through `ai.CheckBaseURL` and the safe client. `AI_ALLOW_PRIVATE_HOSTS` works in the personal edition only.
- Tests use `app/ai/fake` or an `httptest` server; no test calls a real provider or needs a real key. The tables `ai_credentials`, `workspace_ai_settings` and `ai_usage` stay out of sync, export and API scopes (`TestAIExcludedFromExportAndAPI`); extend that test when those routes exist.
- To add a provider, see "Add a provider" in `docs/ai.md`.
- The features (epic 16), read "Features" in `docs/ai.md`: category suggestions (`app/ai/categorize`), the sentence to draft (`app/ai/entry`) and the assistant (`app/ai/assistant`). Untrusted text (descriptions, questions, names) is data in a JSON field, never in the system instruction, and always goes through `ai.Sanitize` (normalize, then redact, then clip: never redact first). Model output is accepted only as the JSON of a schema, for ids and uids the server sent, and never writes: a suggestion is a row to review, the amount of a draft is read by `finance.ParseAmount`, the assistant's figures are the server's own report results. Account and tag names go to the model as opaque labels only. Memory first: `description_rules` (`finance.NormalizeDescription`, learned from manual categorizations and accepted suggestions) answers without AI. Share the AI client with `ai.Shared(app)` (the per-minute window lives in it); tests use `app/ai/aitest` (fake provider, recording queue). `ai:eval` is manual and never runs in CI.

## The Telegram bot

Read `docs/telegram.md` first. The bot lives in `app/telegram/` and talks to the Bot API with `net/http` only (no library, D-010). It is off until `TELEGRAM_BOT_TOKEN` is set: then every bot route (the webhook and `/settings/telegram`) is 404 and no worker starts.

- A chat links only through a single-use code made for the signed-in person (`Store.NewCode`, hashed, 10 minutes) and spent by one conditional `UPDATE` inside the transaction that writes the link (`Store.Redeem`). Never link by account id, email or password, and never add a route or a field that takes a chat id.
- Authorization is read at every message and every tap: `Bot.accessTo` takes the role from the membership now, and `access.can` intersects the bot's fixed scopes (`telegram.Scopes`) with the role ceiling of epic 14. A new command names its scope there. The only delete the bot has is the 60 second undo of the entry it just saved.
- Every update begins with `Store.ClaimUpdate` (unique `update_id`). A command or tap is idempotent by construction: drafts are consumed with a conditional update and the draft reference is the transaction uid.
- Only private chats are served. Anything sent to the chat goes through `EscapeHTML` (the builders of `format.go` do it themselves); money is `finance.ParseAmount` in and `finance.FormatAmount` out.
- The token is a `config.Secret`; the client scrubs it from every error and prints `[redacted]`. Never log a token, a secret, a link code or the text of a message: log update ids and error kinds only (`TestSecurity_TokenNeverInLogsOrResponses`).
- The Telegram tables have no `workspace_id` (they are on the allow-list of the isolation guard): a link belongs to a person and the workspace comes from the live membership. Rate limits are counted in `telegram_counters`, not in `RATE_LIMIT_STORE`.
- Alerts: `telegram.Channel` is an `alerts.Channel`, attached with `telegram.Attach`; a person opts in with `alerts.Service.SetTelegram`. A failure is logged and never fails the alert job.
- Tests use `tests/fakes/telegram.go` (a fake Bot API) and `TELEGRAM_API_BASE`; the browser spec uses `e2e/fake-telegram.mjs`. No test calls the real API or needs a real token. Add a user-facing text in all three languages of `app/telegram/lang/` (a test keeps them equal) and the page strings in `resources/js/i18n/*/telegram.ts`.
- Settings: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`, `TELEGRAM_MODE`, `TELEGRAM_WEBHOOK_SECRET`, `TELEGRAM_WEBHOOK_URL` (`.env.example`); commands `telegram:set-webhook` and `telegram:info`.

## Billing

Read `docs/billing.md` first. Billing is saas only (D-003): the personal edition registers no billing route, webhook or page and reads no Stripe or AbacatePay setting.

- Access is derived: `workspaces.Service.Entitled` is the only place that decides, and `Limits` uses it. A Stripe subscription is Pro when it is `active` or `trialing` and `access_revoked_at` is empty; a PIX entitlement when it is not revoked and `valid_until` is in the future. Never store a plan flag.
- Access changes only from a verified webhook or from a re-read of the charge at the provider, never from a redirect or a client claim. Stripe: `/stripe/webhook` (signature and 5 minutes of tolerance from `contrib/stripe`). AbacatePay: `/abacatepay/webhook` (shared secret in constant time from a header or a path segment, never the query string; HMAC signature; 64 KiB cap), and the body only names the charge: `HandlePixEvent` re-reads it.
- Refunds and disputes revoke through `access_revoked_at`, `revoked_reason` and `revoked_ref`, which `SyncSubscription` never writes. The handlers read the object from the API and write with conditional `UPDATE`s, so a replayed or out-of-order event changes nothing twice.
- PIX activation is one conditional `UPDATE ... WHERE status IN ('pending','expired')` whose affected rows are checked, in the same transaction as the entitlement change. A charge becomes `expired` only when the provider says so. Months add with `timeutil.AddMonths` from `anchor_at`, so stacked payments do not drift.
- Amounts are `int64` cents from the server: `config.Pix.Amount(months)` (`PIX_PRICE_PRO_MONTHLY_CENTS` times the months, only the months in `PIX_MONTHS_OPTIONS`). The request names months and nothing else.
- Only the owner (`billing.manage`) starts a PIX charge, polls it or opens the portal. The poll is `GET /billing/pix/{ref}` (rate limited, 404 for another workspace's reference). The billing tables (`pix_payments`, `pix_entitlements`, `billing_events`) are server-only: no `uid` column, `workspace_id` with a leading index, members of `models.TenantModels`.
- Provider error text and secrets never reach a log, response or audit entry: wrap errors with `sanitizeStripe` or `providerError`, log references and kinds only. Payment records follow D-022: after a deletion only the amount, date, provider reference and a non-reversible subject reference are kept for 5 years (no legal review of that default).
- Settings: `STRIPE_*`, `ABACATEPAY_API_KEY`, `ABACATEPAY_WEBHOOK_SECRET`, `PIX_PRICE_PRO_MONTHLY_CENTS`, `PIX_MONTHS_OPTIONS` (`.env.example`). PIX is on when the API key is set; a production saas boot then requires the other three.
- The job `billing_reconcile` (every 6 hours) re-reads PIX charges that can still change. `ABACATEPAY_API_BASE` and `STRIPE_API_BASE` point at fakes: the tests (`fakeStripe`, `fakeAbacatePay` in `tests/`) and `bunx playwright test e2e/billing.spec.ts` (a saas server on port 3918 and `e2e/fake-abacatepay.mjs`); production ignores the AbacatePay one.

## Data lifecycle

`app/privacy/` holds the export, the deletion and the purge (epic 34). Deletion is two steps: a request moves a workspace (`workspaces.state = 'pending_deletion'`, `purge_at`) or an account (`users.deletion_requested_at`, `purge_at`) into a 30 day grace period, and the job `privacy_purge` (daily, idempotent) erases it when the date passes.

- Re-authentication: every action here asks for the current password (`PrivacyHandlers.confirmPassword`, rate limited by `privacy.confirm`). The export is `POST /account/export` then a one-time, 5 minute `GET /account/export.json`; it names every field (`app/privacy/export.go`) and never reads a hash, secret, token value or AI key.
- Grace period: a pending workspace is read-only on every surface. The checks are `Config.Frozen` in `operations.Invoke` (REST, CLI, MCP; code `workspace_pending_deletion`, 423), `workspaces.RefuseWritesWhilePending` for the web group, `access.can` for the Telegram bot and `ErrWorkspaceDeleted` (410 `workspace_deleted`) for every sync call. A new surface that writes needs its own check and a case in `TestPendingDeletionRefusesWrites`. Only the owner can request or cancel a workspace deletion (and must type its exact name); the personal edition refuses it (use "Erase all local data").
- Account deletion is refused while the person is the only owner of a workspace with other members. Workspaces where they are the only member enter the grace period with the account (same timestamp, so cancelling brings them back); every credential ends at once (`Accounts.RevokeAllAccess`, Telegram links) and a pending account is sent to `/account/deletion`, which never cancels by itself.
- The purge: `purgedTables` (`app/privacy/purge.go`) classifies every table with a `workspace_id`, children first; a table that is not listed stops the purge (`TestPurgeClassifiesEveryTable`), so a new tenant table must be added there. `TestPurge` seeds every such table from the schema, purges one workspace and compares another. Rows go in batches of 500, every statement scoped by the workspace id; tables without a `workspace_id` that point at it (OAuth state, `access_tokens.resource`, Telegram rows) are handled in `purgeWorkspaceEdges`. A subscription that cannot be cancelled (`CancelWorkspaceSubscriptions`, idempotent) blocks the purge and logs an `alert:` line; the other subjects go on.
- What is kept: `privacy_audit` (event, time, HMAC subject reference), `payment_records` (amount, date, provider reference, subject reference, for `PAYMENT_RECORD_RETENTION_YEARS`, default 5, D-022) and `purged_tokens` (public token ids, so a phone that syncs late hears 410 instead of 401). These three have no `workspace_id` and are on the allow-list of the isolation guard.
- Personal edition: `POST /account/erase` (owner, password and the word `ERASE`) closes the database, removes it with its `-wal`, `-shm` and `-journal` files and ends the process; Docker restarts it empty (`restart: unless-stopped`), the desktop app starts empty the next time it is opened.

## Reports and exports

Read `docs/export-format.md` first.

- Reports are functions of `reports.Service` that return plain structs (`CashFlow`, `ByCategory`, `ByAccount`, `ByTag`, `NetWorthSeries`, `Compare`); the page (`GET /reports`) and the future public API share them. A period is `reports.Period` (`NewPeriod`: presets or custom dates, workspace-local, never floats); its `Previous` has the same length (whole months go back the same number of months). All of them go through `workspaces.Scoped`, leave out transfer legs and deleted rows, and sum in Go from grouped queries with clamping at `capCents` (never a SQL `SUM`). Percentages are basis points from integers (`ratio`, `changeBps`), `n/a` when the previous value is zero.
- The CSV (`GET /transactions/export.csv`, any role that can read) takes the filters of the transaction list, streams through `finance.EachTransaction` (keyset chunks, so no cursor holds the one SQLite connection), refuses more than `export.MaxCSVRows` with a 413 before the first byte, and writes every text cell through `finance.SpreadsheetSafe`. The amount is `finance.FormatDecimalCents`. The JSON (`GET /workspace/export.json`, `data.manage`: owner and admin) is built from the explicit types of `app/export/json.go`: a new column reaches it only when added there and to `docs/export-format.schema.json` (`additionalProperties: false`), and `TestSecurity_JSONExportHasNoSecrets` lists the names that may never appear. Both share the limit `config.ExportLimit` per workspace and hour.
- On the page, every chart sits in `ChartWithTable` (the chart is `aria-hidden`, the table is read by screen readers and swaps in with "Show as table"); `resources/css/print.css` shows the tables and hides the shell. The `x` action (`export-transactions`) is registered by `useExportAction` on the transactions and reports pages; `g r` is the `reports` nav item.

## Rules that never bend

- Money is `int64` cents (D-005). Amounts are stored in clear so SQL can sum and filter. Never use floats for money.
- Every domain table carries `workspace_id`, and every query goes through the workspace scope (D-004). A query that skips the scope is a bug.
- Isolation is tested, not trusted. A new domain model joins `models.TenantModels` (with `SetTenant` and `BeforeCreate`) and its table has an index that starts with `workspace_id`; a table with no `workspace_id` goes on the allow-list of `tests/isolation_guard_test.go`, with a reason. A new workspace route that takes an id needs a case in `tests/cross_tenant_matrix_test.go` (the foreign id answers 404, never 403 or 200). Both tests fail until it is done.
- Synced tables follow the [sync data model](docs/specs/sync-data-model.md). `accounts`, `categories`, `transactions` and `budgets` carry `uid` (ULID, the id on the wire), `version` (bumped by a database trigger, so re-read the row after a write) and `deleted_at` (soft delete: never `ForceDelete`, never a physical `DELETE`; only `changes.Compact` purges). A new synced table embeds `orm.SoftDeletes`, joins `changes.Register`, gets its triggers from `changes.InstallTriggers` in the migration (after any step that rebuilds the table, because a rebuild drops triggers; rebuild with `schema.DropTriggers()` and reinstall), and its unique indexes are partial (`WHERE deleted_at IS NULL`). Money fields stay within `models.MaxCents` (2^53 - 1): `models.CheckCents`. `TestIsolationGuard` fails for a table with `uid` that is not registered or lacks triggers.
- Accounts and transfers. A balance is derived (`finance.AccountBalances`, `NetWorth`; the dashboard total is `NetWorth`), never stored or edited. A transfer is two transactions that share `transfer_uid` (an expense leg on the source, an income leg on the destination, no category), written in one database transaction under the workspace lock by `CreateTransfer`, `UpdateTransfer` and `DeleteTransfer`. Transfer legs are excluded from income, expense, category spending, budgets and the monthly quota (`WhereNull("transfer_uid")`); deleting or restoring a leg or an account takes the other leg along; an ordinary edit of a leg is refused. Archived accounts (`archived_at`) leave the plan quota and the pickers but keep their history and balance. A new column on a synced table goes in `Fields` of its `changes.Register` entry or on the server-only list of `TestSyncFieldsCoverColumns`.
- Categories, tags and import. A category nests one level (`parent_id`, same kind as the parent), carries a `color` token name and an `icon` name from `models.CategoryColors` and `models.CategoryIcons` (never free hex), and can be archived (hidden from pickers, refuses new entries, keeps its history). Deleting one is `DeleteCategoryReassigning`: what used it moves to a category of the same kind in one database transaction, and transfer legs are never touched. Tags are tenant rows (`tags`, joined by `transaction_tags`), unique per workspace in any letter case, at most 10 per transaction and 200 per workspace; a transaction save names its tags and the service creates the missing ones. The join is synced as the `tag_uids` column of the transaction (`Entity.JSON`), which the service keeps equal to the join rows. A transfer leg takes no tags.
- Credit cards. A card is an account of kind `credit_card` (made only with its card: `CreateCard`, never `CreateAccount`, and never edited as a plain account) plus a synced `credit_cards` row (limit, `closing_day`, `due_day`, default payment account, `brand` from `finance.CardBrands`, `last4`; never a number, expiry or security code). A statement has no table: `transactions.statement_ref` is its closing date, set on write for purchases on a card account (create, edit, import) and on the card leg of a payment. Dates come from the pure `closingDate`, `statementFor` and `dueDate` (`app/finance/statements.go`). Status (`open`, `closed`, `paid`, `overdue`) is derived. `PayStatement` is a transfer from a non-card account; it is never an expense. Changing the closing day moves only unpaid statements, trashed rows included (`recomputeStatements`). Deleting an account takes its card along and clears the card default that named it; restoring brings the card back. Limit used is `max(0, -balance over all dates)`.
- Recurrences and installments. Read `docs/specs/recurrence.md` first; `testdata/recurrence-vectors.json` is the contract the Go engine (`app/finance/recurrence.go`) and the TypeScript one (`resources/js/lib/recurrence.ts`) both pass. A rule (`recurrences`, synced entity `recurrence`) computes the k-th date from its start date and k, always through `timeutil.AddMonths` (a start on the 31st clamps to month ends and never drifts). `GenerateDue` (job `recurrences_generate`, hourly; also run when a rule is created or edited) makes the due occurrences through `persistTransaction`, one database transaction per rule under the workspace lock, so the quota stays atomic and two runs never double a row. A generated transaction carries `recurrence_uid` and `occurrence_on`; the unique index counts soft-deleted rows, and `generated_through` (only moved to the last processed occurrence) keeps a deleted occurrence out after compaction. A failing rule stores `last_error` and is retried; it never blocks another. Deleting an account deletes its rules, deleting a category moves them (trash included). Installments (`CreateInstallments`, 2 to 60 parts, one database transaction) split with `SplitInstallments` (the first `total % parts` parts get one extra cent) on `AddMonths` dates, each part through the normal path (its month quota, its card statement). `Upcoming` merges future-dated rows with virtual occurrences, never stored. `TxInput.recurrenceUID`, `occurrenceOn` and `installment` are unexported on purpose: only the service sets them.
- Statement import reads untrusted files: `StatementParser` (`CSVParser`, `OFXParser`) bounds size (2 MiB), rows (20000, refused beyond, never cut), cells and columns, and a row it cannot read is a reported failure. The OFX scanner resolves no entity and refuses a DTD, CDATA or comment. Amounts go through `ParseAmount` and nothing else (never `ParseFloat`). `import_hash` (SHA-256 of account, date, signed amount, normalized description, or the FITID) skips rows the account already has unless the import allows duplicates; `RunImport` is one database transaction, so a failed import leaves nothing and a second run does nothing. An imported row is an ordinary entry, never a transfer leg. Text is stored as typed: every exporter must write text cells through `finance.SpreadsheetSafe`.
- Budgets, goals and alerts. A budget is a monthly limit of an expense category (it counts the spending of its subcategories) or, with no category, the overall budget (`models.Budget.CategoryID` is null; one live per workspace); `rollover` adds last month's unspent part, never negative and never chained, only for a budget that already existed then. Spending is `Service.spendingOf`: one grouped query over non-transfer, non-deleted expenses, multiplied and added in Go with clamping at `spentCap` (never a SQL `SUM`, which fails on overflow). A month from a request is checked by `finance.ValidMonth` (strict, years 1900 to 2999). Goals (`goals`, `goal_contributions`, both synced) hold manual contributions that never move money; their progress, the monthly amount needed (`monthsUntil`, `AddMonths` clamping) and the projected date are derived in `goalStatus`. Alerts live in `app/alerts`: `Evaluate` returns the notifications that should exist from current data, `Run` inserts the missing ones (unique `(workspace_id, user_id, kind, subject_key)` is the dedupe, a refused insert is the answer) and sends the mail of rows it claims with a conditional `UPDATE ... SET emailed_at` (released when the send fails). The write path never mails: it calls `finance.Service.RequestAlerts`, which enqueues the job `alerts_evaluate` and ignores a failure (the hourly run catches up). The kinds and their subject keys are listed in `app/alerts/kinds.go` (the contract for the Telegram channel of epic 17: implement `alerts.Channel`). Defaults: in-app for everyone, mail for owners and admins, never for viewers (`alerts.effective`). A notification belongs to one person: no path names another user, and a foreign id is a 404. The page prop of the notification list is `items`, because `notifications` is the shared prop of the header bell.
- The sync protocol. Read [docs/specs/sync-protocol.md](docs/specs/sync-protocol.md) first; `testdata/sync/*.json` is the contract the server (`tests/sync_scenarios_test.go`) and the mobile engine both pass. The server is `app/sync` (devices, pull, snapshot, push) behind `/api/v1/sync/*` (scope `sync`, header `X-Sync-Protocol: 1`, `X-Device-Id`; REST only). Every writable column of a registered entity needs a wire type in `app/sync/fields.go` (`TestSyncEveryRegisteredEntity` fails otherwise); references travel as `<name>_uid`. A push is one `BEGIN IMMEDIATE` transaction, a savepoint per mutation, through `changes.Merge`; it never trusts `version`, `workspace_id` or timestamps, resolves every uid inside the token's workspace only, checks the role per entity (`abilityFor`), the money (`finance.ParseAmount`, `models.MaxCents`) and dates like the services, and applies deletes and restores through `finance.Service.DeleteIn` and `RestoreIn` (the cascades of the services, inside the batch transaction). Results are stored by `op_id` for 30 days (`sync_ops`, pruned by `sync_ops_prune`), so a retry changes nothing. Pull reads the log and the rows in one read-only transaction and never writes before answering: `next_cursor` is the seq of the last change read, and SQLite hands out seq inside the single write transaction, so a late commit is never behind a cursor. A new synced entity needs its field specs, its role ability in `abilityFor` and, when it has a plan limit, its check in `Service.quota`.
- Roles are enforced on the server: `owner`, `admin`, `member`, `viewer` (`app/workspaces/policy.go` holds the table of abilities). Every write handler starts with `h.can(c, ability)`; hiding a button is never the check. The workspace has exactly one owner: only `TransferOwnership` moves it, and every change of members runs under `lockWorkspace`.
- "Today" and "this month" come from the workspace timezone (`finance.Service.Today(ctx)`, `Month(ctx)`). Month arithmetic goes through `app/timeutil` (`AddMonths`); `AddDate` with a month argument is banned elsewhere (a test enforces it).
- Workspace routes are rate limited (`config/limits.go`: reads and writes per user, imports and invites per workspace). The Stripe and Resend webhooks are not limited by IP; their signatures are the check. Failed two-factor codes are limited per account as well as per IP.
- Sensitive workspace actions (roles, ownership, members, invites, settings) write `audit_events` through `Service.record`.
- Commits follow Conventional Commits with a scope from `.github/scopes.txt`; see `.agents/rules/commits.md`.
- Branches and releases follow `.agents/rules/git-and-branches.md`: never commit to `main`, never push, never edit `CHANGELOG.md` by hand.
- Everything in the repository is in English.
- Never commit secrets. `.env` is ignored; `.env.example` holds placeholders only.

## Offline-first personal edition

Read `docs/offline.md` first (D-027). The personal edition (desktop and local Docker) boots, migrates, renders and runs every core feature with no network, and makes no outbound connection unless the person turned an integration on (AI, Telegram, Google sign-in, a real mail server).

- The rules live in `app/offline` and are applied by `bootstrap.New` (`offline.Gate`, a provider plus the `networkTags` view function), keyed on the edition. Never add an `if personal` for network behavior elsewhere, and never add a CDN, remote font, image, script, analytics or update check; the CSP is `default-src 'self'` and stays so.
- A new outbound call (a provider, a webhook, a fetch of a remote document) must be off until configured, must fail with a plain message when there is no network, and gets a row in `docs/offline.md`. Screens that need the internet say so in en, pt-BR and es.
- Mail in personal is `offline.BestEffort`: a connectivity failure never fails or changes the answer of a flow (dropped and logged on the inline queue, retried on a real one); other mail errors propagate. saas is untouched.
- The guard is `tests/offline_test.go` (Go: `http.DefaultTransport` and `net.DefaultResolver`) and `e2e/offline.spec.ts` (browser). Extend the journey when a feature gets a new page or job. Both are blind to a bare dial to an IP literal; the container check with `--network none` in `docs/offline.md` covers it.

## Security and fuzzing

Read `docs/security.md` (the threat model: assets, boundaries, one STRIDE table per surface with the control and the test) and `SECURITY.md` (how to report). A new surface, asset or boundary updates the tables in the same change. `docs/qa/rounds.md` records every problem the quality campaign finds (`QA-NNN`), fixed with a test first.

- The attack suites are `tests/security_*_test.go`, every case named `TestSecurity_<Area>_<Case>` (`go test ./tests/... -run TestSecurity_`; `-race` is part of the gate). A new route that changes state needs nothing extra for CSRF (`TestSecurity_Web_CSRF` walks the router); a new MCP or OAuth rule needs a case in `tests/security_mcp_test.go`.
- Fuzz targets are `Fuzz*` functions in `tests/fuzz_*_test.go`, all in the one package `tests` because `go test -fuzz` refuses several packages. Seeds are `f.Add` calls and `tests/testdata/fuzz/<Target>/`; a crash input is committed there as a regression seed. `go run ./scripts/qa/fuzz-targets -packages` lists `<target> <package>`; `.github/workflows/fuzz.yml` runs each for 30 seconds on a pull request that touches a parser and for 10 minutes nightly. The targets that go through the app (`FuzzSyncPush`, `FuzzMCPJSONRPC`, `FuzzOAuthAuthorize`, `FuzzOAuthToken`) build their app once with the `testing.F` (`oauthtest` takes a `testing.TB`) and use a new client address per input (`nextIP`) so rate limits never decide the answer.

## Docker and deployment

- The database is SQLite only, one file in WAL mode (`/app/storage/database.sqlite` in the `storage` volume), and the app is one replica. There is no PostgreSQL and no database container; do not add one.
- The reverse proxy and static server is Caddy, never nginx. Every `image:` and `FROM` carries an exact version tag and a digest, never `latest`. The Caddy image is pinned in `compose.prod.yaml`.
- `compose.yaml` is the local stack (app on `127.0.0.1:3000`, Mailpit, edition `personal` unless `APP_EDITION` says otherwise). `compose.prod.yaml` is the VPS stack: no published port on `app`, `TRUSTED_PROXIES` set to the compose subnet so rate limits see the real client address.
- Sessions are rows of the `sessions` table (`SESSION_DRIVER=database`, set as the default in `bootstrap.New` for both editions; the framework creates the table and prunes it hourly), never encrypted cookies: logout deletes the row. The test harness pins `SESSION_DRIVER=cookie`; a test of sessions passes `"SESSION_DRIVER": ""` to run on the application default.
- The version is `config.Version`, set by the Dockerfile `ARG VERSION`; the `about` command (`bootstrap/about.go`) shows it and `/up` must not.
- Backup and restore use the framework's `db:backup`; never copy the live file. `user:reset-password -email <address>` recovers a locked-out owner from the server console.
- `.github/workflows/image.yml` publishes to GHCR and Docker Hub when a release is published; it needs the secrets `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN`.
- On Windows with Git Bash, prefix `docker ... exec` commands that carry `/app/...` paths with `MSYS_NO_PATHCONV=1`.
